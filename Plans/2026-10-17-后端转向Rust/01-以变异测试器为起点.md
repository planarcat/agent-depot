# 第 1 轮：后端转向纯 Rust，变异测试器能否作为起点

> 时间: 2026-10-17 11:07

## 用户提问

能写 rust 吗？我希望整个项目后期后端部分转向纯 rust，这个可以作为一个开始。

（上下文：「这个」指正在讨论的变异测试能力。按《AI开发质量体系-落地方指南》§四，本仓原本记为「跳过（无能力）」。上一轮的推荐方案是用 Python 标准库自研零依赖变异器。）

## 背景与分析

### 1. 后端现状（2026-10-17 实测）

| 项 | 现状 |
|---|---|
| 规模 | `server.py` 1000 行 + `hub/` 6,946 行，最大的是 `mod_skills` 1388、`scanners` 1344、`mod_mcp` 1156、`store` 586、`mod_memory` 534、`watcher` 511 |
| 依赖 | **纯标准库**：`http.server`、`sqlite3`、`subprocess`、`threading`、`urllib`、`hashlib`、`csv` 等；文件监控走 kqueue（stdlib `select`） |
| 对外契约 | 41 条 `/api/*` 路由 + SSE `/api/events` + 静态托管 `web/`；行为靠环境变量注入（`AGENT_HUB_DIR`、`HUB_PORT`、`HUB_CLAUDE_PROJECTS`、`CODEX_HOME`、`HUB_OPENCODE_DB`、`HUB_WATCH`…） |
| 存储 | SQLite（sessions / messages / cursor / ledger / config / lineages / migrations） |
| 外部进程 | `git`（gitsrc）、MCP 握手（mcpverify）、`casr`（migrator） |
| Rust 现状 | 只有 Tauri 外壳 `desktop/src-tauri`（93 行，依赖仅 `tauri = "2"`，**零 `#[test]`**），目前用 `bash -c` 拉起 Python 服务 |
| 工具链 | cargo / rustc 1.98.1、clippy、rustfmt、rust-analyzer 齐全；`cargo-mutants` 未装 |

### 2. 测试能不能当迁移安全网

| 套件 | 性质 | 迁移后命运 |
|---|---|---|
| `test_hub.py` | **126 次 HTTP 调用**，起 `server.py` 子进程；只有 1 处直接 import `hub.store` | ✅ 基本是**语言中立的契约测试**：把子进程换成 Rust 二进制、环境变量保持一致，就能原样复用（那 1 处白盒改造即可） |
| `e2e.mjs` / `e2e_sandbox.mjs` | 真 Chrome 走 HTTP | ✅ 完全语言中立，原样复用 |
| `test_skills` / `test_mcp` / `test_manual_mcp` / `test_extras` / `test_watcher` | 直接 `import hub.*` 的**白盒测试** | ⚠️ 迁到哪个模块，就要把对应测试改写成 `cargo test`，否则判据会凭空消失 |

**结论**：迁移的安全网是现成的（HTTP 契约 + E2E），前提是它**先得是绿的**。当前 `test_hub` 4 红、`test_skills` 6 红、`test_manual_mcp` 1 红，契约本身不可信，必须先修绿。

### 3. 「变异测试器作为 Rust 第一块」的判断

**有一个结构性问题：它要变异的对象（Python 后端）正是将来要被淘汰的那部分。**

- 迁移期：Python 代码需要变异测试。如果用 Rust 写，就要解析 Python。
  - 要么引入 Python 解析器 crate（如 `rustpython-parser`，**可用性与维护状态待核实**）；
  - 要么自己做字符级替换，会误改字符串和注释，变异不可信。
- 迁移完成后：Rust 代码已经有成熟的 `cargo-mutants`，自研的 Python 变异器就成了一次性产物。

所以**不建议让「Rust 写的 Python 变异器」当第一块**。但用户的直觉是对的：第一块应该是**低风险、不碰产品行为、却能把 Rust 地基搭起来**的东西。质量工具链正好符合这个条件。

### 4. 「纯 Rust」与「零依赖」原则冲突，必须先改口径

Rust 标准库**没有** HTTP 服务器、SQLite、JSON。真正的后端迁移一定会引入 crate，常见的如：

- `rusqlite`（bundled）
- `serde` / `serde_json`
- 一个 HTTP 库（`tiny_http` 或 `axum` + `tokio`）
- 可能还有 `notify`（文件监控）

本仓现有的「零依赖」原则，需要改写成 Rust 语境下的新口径，例如：

> 产物零运行时依赖（单二进制）+ crate 白名单 + `Cargo.lock` 入库锁定

## 建议与回答

### 推荐路线：先搭地基，再按「绞杀者模式」逐模块迁移

```
Phase 0  Rust 地基 = 质量工具链 xtask（不碰产品行为）
           │  cargo workspace + cargo test/clippy/fmt + cargo-mutants 从第一天就是门禁
           ▼
Phase 1  修绿契约（11 红）→ 契约测试改为"可指定后端二进制"（Python / Rust 同测）
           ▼
Phase 2+ 绞杀者迁移：Rust 服务在前，未迁路由反代给 Python 子进程；
         按 watcher → scanners/store → modules → server 逐块替换，
         每迁一块：白盒测试同步改写成 cargo test（判据数 1:1 对账）
           ▼
Phase N  Python 下线；Rust 后端并入 Tauri 进程（单二进制，去掉 bash 拉起）
```

### Phase 0 细化：`xtask` 质量工具链（Rust 第一块）

把现有 Python 质量脚本收进一个 Rust CLI，**只用 std、零 crate**：

| 子命令 | 替代 | 说明 |
|---|---|---|
| `xtask spec-guards` | `scripts/check_spec_guards.py` | 纯文本扫描 |
| `xtask lint-styles` / `lint-baseline` | `tests/lint_styles.py` + 未做的 lint 基线 | 基线要处理分支、合并期误报 |
| `xtask mutate` | 本轮缺口：变异门禁 | 见下 |
| `xtask check` | `tests/check.sh` | 串起全链路，pre-push 调它 |

`xtask mutate` 按「编排器 + 变异提供方」拆开：

- **编排器（Rust）**：复制隔离目录、并行、超时（timeout 记为 killed）、计分、阈值（high 80 / low 60 / break 60）、写 `reports/mutation.json`、`exit 1`。这部分与语言无关，迁移完成后仍可保留。
- **Python 提供方（过渡期）**：一个约 100 行的 Python 标准库 `ast` 脚本，只负责「列出变异点、生成变异源码」。Python 自带的解析器最可靠，不需要引入 crate；Python 下线时它随之删除。
- **Rust 提供方**：直接调用 `cargo-mutants`，不重复造轮子。从 Phase 0 起，xtask 自己的代码就受它约束。

这样 Rust 从第一天起就带着测试、clippy 和变异门禁，迁移期的 Python 变异能力也一起补上了。

### 需要用户拍板的 4 个决策

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| D1 | 「零依赖」在 Rust 下的新口径 | ①只用 std（HTTP / SQLite 全部手写，不现实）②crate 白名单 + `Cargo.lock` 锁定 + 单二进制 ③放开 | **②**；xtask 阶段仍做到零 crate |
| D2 | Rust 第一块做什么 | ①只做变异测试器 ②**xtask 质量工具链（含变异编排）** ③直接迁 `watcher` | **②**：不碰产品行为，地基与门禁一次搭齐 |
| D3 | 迁移模式 | ①绞杀者（Rust 在前、反代 Python）②并行重写后一次切换 | **①**：每一步都可发布、可回退，契约测试全程有效 |
| D4 | 迁移期判据对账 | 白盒 Python 测试退役时，同 PR 内必须给出等价的 `cargo test`，判据数 1:1 对账，否则按「判据减少 = 改松」打回 | 写进 AGENTS.md 卡口第 7 条 |

### 已知待核实

- `rustpython-parser` 当前可用性与维护状态（只在 D2 选①时才需要）
- HTTP crate 选型（`tiny_http` 同步、轻量；`axum` 异步、生态大），Phase 2 再定
- `cargo-mutants` 对 Tauri 工程（含 `build.rs`）的兼容性，装上后实测

## 本轮要点

- 后端是 7.9k 行纯标准库 Python，对外契约是 41 条 HTTP 路由加 SSE 和环境变量；`test_hub`（126 次 HTTP 调用）和 E2E 是语言中立的迁移安全网
- **安全网要先修绿**：当前 11 红，修绿是迁移的前置条件
- 不建议用 Rust 写 Python 变异器：被变异的对象终将下线，Rust 侧已有 `cargo-mutants`
- 推荐把 Rust 第一块定为 `xtask` 质量工具链（零 crate），其中变异采用「Rust 编排器 + 过渡期 Python ast 提供方 + cargo-mutants」
- 「零依赖」原则要在 Rust 语境下改口径（建议：crate 白名单 + `Cargo.lock` 锁定 + 单二进制）
- 迁移采用绞杀者模式；白盒测试退役必须 1:1 对账为 `cargo test`
- 进行中的 lint 基线（未改任何文件）并入 Phase 0，用 xtask 实现
