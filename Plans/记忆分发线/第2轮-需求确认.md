# 记忆分发线 · 第 2 轮：需求确认与决议

> 日期：2026-10-12
> 状态：需求已由用户给出，判断题已裁定，进入待执行方案
> 上一轮：[第1轮-核心原则.md](./第1轮-核心原则.md)（其中 Q1–Q5 被本轮需求覆盖/收口）

## 用户原始需求（2026-10-12）

1. 打开应用或进入页签时，**自动获取**当前所有工具的记忆、会话列表；若数据量大造成性能问题，降级为每个工具提供按钮点击刷新——**最好自动化，按钮做手动兜底**
2. **能力探测**：检查每个工具的记忆能否读取并格式化为中间体、能否写入
3. 页面布局：**左侧=记忆来源**（可读的工具可点击，不可读的置灰）；**右侧=写入去向**（可写的可操作，**不可写的直接隐藏**）；显示均受设置里工具启停的控制
4. **中间体**：所有记忆、会话转化为中间格式，读取→中间体→写入；若不合适可退化为直接读→写——**由 AI 判断**
5. **skill、MCP 同口径**：从仓库拉取的内容应**直接保存到本地中间体**，不需要再点一次按钮才真正落库

## 裁定与决议

### 裁定 1：采用中间体方案（用户第 4 点委托判断）

**判断：读取 → 中间体 → 写入，值得做，不做直连读写。** 理由：

- 各工具记忆文件结构不同（目录布局、文件名、条目组织），没有中间体则每个「源×去向」都要写一条转换路径，N² 膨胀；中间体把它压成 N+M
- 漂移检测需要「上次写出去的内容 + hash」存在 hub 侧，中间体天然承载这个
- hub 要做权威编辑中心（用户第 3 点的左右布局隐含此意），编辑必须落在中间体上，不能落在线外文件

**中间体形态**：登记表（hub.db）+ 内容文件（hub 库目录，按 scope 存放 markdown），与 Skills 本地库同构。

### 裁定 2：权威源口径（第 1 轮 Q2 的收口）

hub 是权威源。工具端自己在会话中写记忆 → 下次扫描发现内容与上次写出的 hash 不符 → 标记**漂移**，提示人工选边，绝不静默覆盖（沿用 Skills 口径）。

### 裁定 3：自动刷新的降级策略（用户第 1 点委托判断）

- 记忆、会话的**列表（元数据）**体积小：进入页签**自动刷新**，会话正文点击时懒加载
- 每个工具扫描加**超时护栏**（约 3 秒）：超时或该工具数据量超阈值 → 该工具自动降级为手动刷新按钮，其余工具不受影响
- 手动刷新按钮常驻，自动化优先但永远可手动

### 裁定 4：能力探测驱动 UI（用户第 2、3 点）

- 扫描时逐工具探测：**可读**（路径存在且可解析）→ 左侧点亮；**可写**（目录存在且可写）→ 右侧显示
- 不可读 → 左侧置灰（保留可见性，用户知道这个工具存在但采不了）；不可写 → 右侧**隐藏**（去向列表只留有效目标，减少噪音）
- 一切以设置页工具启停为总开关

### 决议 5：Skills/MCP「拉取即落库」（用户第 5 点，吸收原 A 项）

- `pull_source` 成功后**自动物化**新增/变更条目进本地库（非 force：本地有改动则标记冲突不覆盖），删除「更新到本地」这个独立步骤的必要性
- 分发时若发现个别条目仍未落库（历史遗留），自动物化后再分发——两道保险
- MCP 无仓库拉取概念，不受影响

### 第 1 轮问题的最终归宿

| 第 1 轮 | 归宿 |
| --- | --- |
| Q1 记忆范围 | 用户画像 + 项目记忆进中间体；会话明细走会话线；topics 跟随项目记忆 |
| Q2 权威源 | 方案甲（裁定 2） |
| Q3 文件映射 | 不再限制「只分全局」——能力探测自动决定各工具可读/可写，能写就显示（比第 1 轮建议更激进，按用户需求执行） |
| Q4 冲突 | 裁定 2 |
| Q5 隐私 | UI 明示去向（右侧列表即所见即所得）；不做自动改写 |
