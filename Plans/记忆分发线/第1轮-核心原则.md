# 记忆分发线 · 第 1 轮：核心原则

> 主题：Agent Depot 补齐原始目标中缺失的「会话记忆」整条线——采集、集中、分发。
> 状态：讨论中（待收敛后产出待执行方案）
> 日期：2026-10-12

## 背景

原始目标：做一个「会话记忆、skill、MCP 的集中分发中心」，由它向各个工具分发内容。

现状盘点（2026-10-12）：

| 内容线 | 状态 |
| --- | --- |
| Skills 分发 | ✅ 可用（8 个工具目标，含漂移检测） |
| MCP 分发 | ✅ 可用（8 个目标，多格式兼容） |
| 会话采集浏览 | ✅ 可用（单向读入；Trae CN 因加密库暂为 0） |
| **记忆** | ❌ **整条线未开工**：各工具的记忆文件各自为政，hub 不采集、不集中、不分发 |

## 本轮要收敛的 5 个核心问题

### Q1 「记忆」的范围界定

各工具的记忆落盘形态不一（以 Trae CN 为例：用户画像 `user_profile.md`、项目记忆 `project_memory.md`、会话明细 `session_memory_*.jsonl`、话题汇总 `topics.md`）。

**建议默认**：第一版只管两类持久记忆——**用户画像**（跨项目）与**项目记忆**（按项目）。会话明细 jsonl 属于「会话线」不进记忆分发；话题汇总 topics.md 是派生物，跟随项目记忆走。

### Q2 权威源与流向（最关键的一问）

记忆和 skill 不同：工具自己会在会话中**写**记忆，不是只读消费者。

- 方案甲：hub 是唯一权威源。首次把各工具现有记忆「登记导入」，之后一切编辑在 hub 做，分发写回工具；工具端自己改了 = 漂移，提示人工处理。
- 方案乙：双向同步。工具照常自己写，hub 定期读入合并，冲突时人工选边。
- 方案丙：只读集中浏览（不写回），先做可视化，分发以后再说。

**建议默认**：方案甲（与 Skills 体系同构：单一出货口 + hash 漂移检测），理由：可审计、行为可预期；工具端写入提示冲突而不静默覆盖。

### Q3 分发目标的文件映射

各工具记忆目录路径不同；项目记忆还要面对「同一项目在不同工具里路径不同」的问题。

**建议默认**：第一版只做**全局用户画像**分发（各工具一个固定映射路径），项目记忆先只采集集中 + 浏览，不写回（映射规则复杂，第二版再定）。

### Q4 冲突与漂移口径

**建议默认**：照抄 Skills 的口径——写回前 hash 比对，目标被外部修改 → 标记冲突、人工选边，绝不静默覆盖。

### Q5 隐私与体量

用户画像/项目记忆含个人偏好与工作内容，分发等于把它铺到所有工具。

**建议默认**：第一版原样分发不做自动改写；在 UI 上明确展示「这条记忆会写到哪些工具」；体量控制（改写代替追加）是编辑侧的事，不在分发层做。
